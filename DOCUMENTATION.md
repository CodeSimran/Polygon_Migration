# Polygon Migration Tool - Documentation

## 2.1 User Flows

### 1. User Login
- **Trigger**: The user lands on `/users/login/` and submits the login form.
- **Data sent**: `username` (email) and `password`.
- **Processing**: The backend uses Django's built-in authentication system. It checks the credentials against the `users_user` table in the PostgreSQL database.
- **External APIs**: None.
- **Database operations**: SELECT query to verify the user exists and the password hash matches.
- **Result**: On success, the user is redirected to the main dashboard (`/`). On failure, an error message is shown.

### 2. Fetch Problem from Polygon
- **Trigger**: User enters a Polygon Problem ID in the search bar on the homepage and clicks "Fetch".
- **Data sent**: `problem_id` via a POST request.
- **Processing**:
  1. The backend (`problems.views.index`) validates the ID.
  2. It generates an API signature using the `POLYGON_API_KEY` and `POLYGON_API_SECRET`.
  3. It makes an HTTP request to Polygon's `problem.info` and `problem.statements` endpoints.
  4. It parses the JSON response to extract time limit, memory limit, constraints, and the problem statement.
- **External APIs**: Polygon API (`https://polygon.codeforces.com/api/`).
- **Database operations**: It checks if the problem already exists in our local DB to disable/enable certain UI buttons.
- **Result**: The UI reloads, and the user sees the fetched problem details (statement, test cases, etc.) displayed on the screen.

### 3. Migrate Problem to Database
- **Trigger**: User selects a difficulty, adds tags, and clicks "Migrate Problem to Database".
- **Data sent**: `problem_id`, `difficulty`, and `tags`.
- **Processing**: 
  1. The backend receives the data and fetches the problem details from Polygon one more time to ensure data freshness.
  2. It parses the tags string into individual tags.
  3. It creates or updates the problem record.
- **External APIs**: Polygon API (to fetch the latest data before saving).
- **Database operations**: 
  - INSERT/UPDATE into `problems_problem` table.
  - INSERT into `contents_tag` table (for any new tags).
  - INSERT into the problem-tag mapping table.
- **Result**: A success message is shown, and the "Migrate Test Cases" buttons become enabled.

### 4. Migrate Test Cases to Database
- **Trigger**: User clicks "Migrate Test Cases to DB".
- **Data sent**: `problem_id`.
- **Processing**: 
  1. The backend calls the Polygon API to fetch all test cases for the problem.
  2. It iterates through the test cases. Since database storage is meant for metadata and not massive files, it intentionally discards the full test case strings.
  3. It saves only the metadata (like the test index and whether it's a sample test).
- **External APIs**: Polygon API (`problem.tests`).
- **Database operations**: INSERT into `problems_testcase` table.
- **Result**: A success message confirms that the test cases were linked to the problem in the DB.

### 5. Migrate Test Cases to Cloud Storage
- **Trigger**: User clicks "Migrate Test Cases to Cloud Storage".
- **Data sent**: `problem_id`.
- **Processing**: 
  1. The backend calls the Polygon API to fetch the actual file contents for all test cases.
  2. It instantiates the configured storage provider (e.g., LocalStorage or GDrive) using the Factory pattern.
  3. It iterates through each test case and streams the input and output strings into files.
- **External APIs**: Polygon API (to fetch the raw strings).
- **Database operations**: None directly for this step.
- **Result**: The files are created in the storage provider, and the user sees a success message.

## 2.2 External Integrations

### Polygon API
- **Endpoints used**:
  - `/api/problem.info`: Fetches memory/time limits and checker info.
  - `/api/problem.statements`: Fetches the HTML problem statement, input/output formats, and notes.
  - `/api/problem.tests`: Fetches the test cases and their actual string contents.
- **Authentication**: We use a cryptographic signature. Every request includes our `apiKey`, the current `time`, and an `apiSig` which is generated by hashing a random 6-character string, the endpoint name, parameters, and our `API_SECRET` using SHA-512.

### Cloud Storage
- **Implementation**: The system uses a `BaseStorageProvider` interface which allows swapping between Azure, AWS, Google Drive, or Local Storage by just changing the `.env` file.
- **File Organization**: Files are organized hierarchically by problem ID.
  - Path: `test_cases/{problem_id}/`
  - Input files are named with just the test index: `1`, `2`, `3`
  - Output/Answer files are appended with `.a`: `1.a`, `2.a`, `3.a`
